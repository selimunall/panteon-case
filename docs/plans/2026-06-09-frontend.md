# Frontend (Leaderboard Screen) Implementation Plan

> **Methodology:** Implementation-first (no TDD). Backend tasks are verified by `tsc --noEmit` + a live curl; client tasks are verified by running the app and inspecting it. **Tests are written last** (Task 7). The **visual craft of the React components uses the `frontend-design` skill** — this plan defines the structure, data flow, and decisions; the skill produces the polished, distinctive UI. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A competitive leaderboard screen where a player instantly sees the prize pool and the week countdown, their own rank and the players around them, the top 100 with a podium, and can smoothly scroll/explore the top 1000 — fast on PC and mobile.

**Architecture:** The existing Vite + React 19 + TS client (`@panteon/client`) talks to the server's read API (`/leaderboard/top|me|page`). The board polls every ~3s (cheap behind the top-100 cache). Names come from a new Redis `profile:{playerId}` decoration on the read path; avatars are generated **client-side** from the playerId (deterministic, no storage, works offline on the deployed domain). The long list is **virtualized** so scrolling never freezes (the legacy bug).

**Tech Stack:** React 19, TypeScript, Vite, `@panteon/shared` types, CSS (component-scoped). No heavy UI deps beyond a tiny virtualization helper (custom windowing — no runtime dependency).

**Depends on:** Plans 1–5 (the read API + seeded data). Reuses `LeaderboardEntry`/`PlayerRankView` from `@panteon/shared`.

**Prerequisite:** `pnpm db:up` + seed; API (`src/index.ts`) and worker (refresher) running.

---

## Design decisions (please review)

- **Display names:** the read endpoints decorate entries with `displayName` from a Redis `profile:{playerId}` string (populated by the seed and by the worker's stub-create). Keeps reads Redis-only.
- **Avatars:** generated client-side from the playerId — initials + a deterministic gradient (hash → hue). No backend, no external service, no storage; renders identically everywhere.
- **"Me" identity (no auth):** the demo picks the current player. Click any row to "become" that player (highlights + reveals their window); a **"Surprise me"** button selects a random rank (incl. outside the top 100); the choice persists in `localStorage`.
- **Live updates:** poll `/leaderboard/top` + `/leaderboard/me` every ~3s. Idle-game cadence; invisible staleness; cheap behind the cache.
- **Layout:** header (prize-pool banner + week countdown + your-rank card) → podium for the top 3 → virtualized list (rank 4 → 1000) with infinite scroll → sticky "jump to me". Responsive PC/mobile.
- **Visual direction:** a distinctive competitive-gaming aesthetic (built with `frontend-design`), not a generic table.

- [ ] **Step 1: Key + profile service**

Append to `server/src/lib/keys.ts`:

```ts
export const profileKey = (playerId: string): string => `profile:${playerId}`;
```

Create `server/src/services/profile.ts`:

```ts
import type Redis from 'ioredis';
import type { LeaderboardEntry } from '@panteon/shared';
import { profileKey } from '../lib/keys.js';

/** Store display names (idempotent overwrite). */
export async function setProfiles(redis: Redis, profiles: { id: string; displayName: string }[]): Promise<void> {
  if (profiles.length === 0) return;
  const pipe = redis.pipeline();
  for (const p of profiles) pipe.set(profileKey(p.id), p.displayName);
  await pipe.exec();
}

/** Attach displayName to entries via one MGET (keeps reads Redis-only). */
export async function attachNames(redis: Redis, entries: LeaderboardEntry[]): Promise<LeaderboardEntry[]> {
  if (entries.length === 0) return entries;
  const names = await redis.mget(entries.map((e) => profileKey(e.playerId)));
  return entries.map((e, i) => ({ ...e, displayName: names[i] ?? undefined }));
}
```

- [ ] **Step 4: Decorate the read endpoints**

In `server/src/services/leaderboard.ts`, after building entries in `computeTop100`, `getPage`, and the `player`/`neighbours` of `getPlayerRankView`, decorate with names. The cleanest is to decorate at the call sites; update the three to accept the redis they already have and call `attachNames`. Change `computeTop100` to decorate (so the cache JSON carries names):

```ts
import { attachNames } from './profile.js';
// ...
export async function computeTop100(redis: Redis, weekId: string): Promise<LeaderboardEntry[]> {
  return attachNames(redis, await rangeToEntries(redis, weekId, 0, 99));
}
export async function getPage(redis: Redis, weekId: string, offset: number, limit: number, cap = 1000): Promise<LeaderboardEntry[]> {
  const start = Math.max(0, offset);
  if (start >= cap) return [];
  const stop = Math.min(start + limit - 1, cap - 1);
  return attachNames(redis, await rangeToEntries(redis, weekId, start, stop));
}
```

In `getPlayerRankView`, decorate the combined `[player, ...neighbours]` once, then split back:

```ts
  const decorated = await attachNames(redis, [player, ...neighbours]);
  return { weekId, inTop100, player: decorated[0]!, neighbours: decorated.slice(1) };
```

(`top100Cache` already calls `computeTop100`, so the cache now includes names; routes need no change.)

```ts
import type { LeaderboardEntry, PlayerRankView } from '@panteon/shared';

const BASE = import.meta.env.VITE_API_BASE ?? '/api';

async function get<T>(path: string): Promise<T> {
  const res = await fetch(`${BASE}${path}`);
  if (!res.ok) throw new Error(`${res.status} ${path}`);
  return res.json() as Promise<T>;
}

export interface TopResponse { weekId: string; entries: LeaderboardEntry[]; }
export interface PageResponse { weekId: string; offset: number; cap: number; entries: LeaderboardEntry[]; }

export const fetchTop = () => get<TopResponse>('/leaderboard/top');
export const fetchPage = (offset: number, limit = 50) => get<PageResponse>(`/leaderboard/page?offset=${offset}&limit=${limit}`);
export const fetchMe = (playerId: string) => get<PlayerRankView>(`/leaderboard/me?playerId=${playerId}`);
```
